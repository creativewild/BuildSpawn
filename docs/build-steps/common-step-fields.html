Fields every runner has

Most runners end with the same fields: working directory, environment variables, test reports, container settings and, for script runners, how stderr is shown. They work the same in every runner.

When to use it

Read this page once. Each runner page then only lists what is special about it, and points here for these fields.

How to set it up

  1. Open the build configuration and click Settings › Build Steps.
  2. Add a step or click Edit on one. Scroll to the end of the runner's fields.
  3. Fill in the fields below and click Save.

Every field

FieldWhat it doesDefaultExample
Working directoryRelative to the workspace. Empty means the workspace itself. It is created if missing. Inside a container it must be inside the workspace.EmptyBuild/Tools
Environment variablesOne NAME=value per line. They are stored in plain text in the build configuration: use a password parameter for a secret. A line that is not NAME=value fails the step.EmptyUE_BUILD_TARGET=Game
Test reportsJUnit XML files, as an Ant pattern relative to the workspace. They are recorded as test results, also when the step fails.Emptyreports/*.xml
Run step within containerThe step runs in a new container from this image, with the workspace mounted, and the build continues on the agent. The agent then needs Docker, not the tool. Empty runs the step on the agent. Parameters, the variables above and what the build adds go in; the agent's own variables and PATH stay out.Emptyalpine:3.20
Image platform (More options)Any takes what Docker on the agent runs. Linux or Windows asks for that kind of image. On a Windows agent a Linux image sees the workspace at /workspace. A Windows image is refused on Linux and macOS agents.AnyLinux
Pull policy (More options)If missing on the agent, Always or Never.If missing on the agentAlways
Force pull on each run (More options)Pulls the image on each run, whatever the pull policy says.OffOn for a moving tag such as latest
Additional run arguments (More options)One argument per line, such as --network=host. They go to docker run as given and nothing checks them. Anyone with Configure on the build configuration chooses them. Do not put a secret here.Empty--memory=4g
Format stderr output asCommand Line and PowerShell only. Lines written to stderr show in orange (Warning) or red (Error) in the log. The text itself is not changed.Plain, as in the log todayWarning

Docker, Docker Compose and Xcode Project have no container settings: they use the tool of the agent itself.

Use build parameters in script text

In the script of Command Line, PowerShell, Python, Node.js, Kotlin Script and C# Script steps, write %name% to use a build parameter. Secrets are never written into script text. Read them from the environment instead. See The script editor.

What you see when it runs

The console prints the command that was started, after a $, then its output. With a container image, a line says that the step runs in the container. When test reports match, the build gets a Tests tab, and a failed test makes the step unstable.

Problems and fixes

ProblemWhat to do
This step needs a workspace and the build has noneRun the build on an agent that has a workspace.
Line N of the environment variables is not NAME=valueFix the line. One NAME=value per line.
This step runs in a container and docker could not be started on this agentInstall Docker on the agent, or clear Run step within container.
Docker on this agent did not answerStart the Docker service on the agent.
A Windows image runs only on a Windows agentRun the step on a Windows agent or choose another image platform.
The image name is emptyCheck the parameter the image name comes from.
The workspace … is on a network share / holds a colonDocker cannot mount it. Use a local workspace folder.
Test reports not recorded: JUnit test reporting is not installedAsk an administrator to turn JUnit test reporting on.
Exit code 125 from a container stepDocker itself failed to run the container. Read the line above it in the log.
