The build name and status text

A build script can give its build a meaningful name, such as 1.4.212-CL48213, and a short status text, such as Uploaded to Steam branch qa. Both show on the build page, in History and on chain pages.

When to use it

A build number like #212 says little. A name with the game version and the changelist tells the QA team which build to test. A status text says what the build did when "Success" is not enough: where it uploaded, or how many tests passed.

Name a build

  1. In a step of the build configuration, print this line. Put it in a PowerShell, Command Line or any other script step. 
    Write-Host "##buildspawn[buildNumber '1.4.%build.counter%-CL%build.vcs.number%']"
  2. Run the build. The name replaces the plain number in the header of the build page, in the History list and on chain pages.
  • The build's real number, its address and its links stay the same.
  • If several steps print the message, the last name counts.
  • The name can be up to 200 characters. A name that refers to an unknown parameter, or to a password, is refused. The build keeps its name and the log says why.
WriteTo get
%build.counter%The build number, for example 212.
%build.vcs.number%The changelist or commit the build used.
%build.triggeredBy.username%The user who started the build.
%name%A build parameter, or a value an earlier step set with setParameter.
{build.number}The build's name so far, to add to it.
%%One percent sign.

Set the status text

  1. In a step, print this line: 
    Write-Host "##buildspawn[buildStatus text='{build.status.text}, uploaded to Steam branch qa']"
  2. When the build ends, the text shows on the build page and in History. {build.status.text} stands for the text the build would show anyway, so a build that says Tests passed: 120 now says Tests passed: 120, uploaded to Steam branch qa.
AttributeRule
textThe new status text, up to 500 characters. The last text a build sends counts. A text that holds a password parameter's value is refused.
statusOptional: SUCCESS, UNSTABLE or FAILURE. It is applied when the build ends. It can only make the result worse, never better: a failed build stays failed even if a script sends SUCCESS.
# PowerShell: mark the build unstable if the upload was partial
if ($uploaded -lt $total) {
  Write-Host "##buildspawn[buildStatus text='Uploaded $uploaded of $total depots' status='UNSTABLE']"
}

Know who started the build

A script can read %build.triggeredBy.username%, or the environment variable BUILDSPAWN_TRIGGERED_BY. It holds the user who started the build. It follows chains and retries, and is empty for a schedule or a version control trigger.

What you see

  • The build's name in the header, History list and chain pages.
  • The status text next to the result chip, once the build has finished.

Problems and fixes

ProblemWhat to do
The name did not change.Spell the message exactly: ##buildspawn[buildNumber '...'], with single quotes. Only a step's own output counts: the same line in a commit message or after the step ended is refused. Search the console for the line. A refusal says why.
The status stays Success although I sent status='FAILURE'.The status is applied when the build ends. Check the log for a refusal line.
I want status='SUCCESS' to turn a failed build green.It cannot. A script can only make the result worse.
