Passing parameters in a build chain

A build can tell the builds it depends on what to build, and can read what they used. Both work along a chain of snapshot dependencies.

Take a release build that depends on a Windows build and a PS5 build. Both need to be built as Shipping, and each for its own platform. You set that once, in the release build, and the dependencies get it.

A chain is made of snapshot dependencies. Artifact dependencies copy files between builds; they are on the same page.

Down the chain: reverse.dep

A parameter named reverse.dep.<ID>.<name> sets <name> in the dependency build of the build configuration with that ID. <ID> is the build configuration ID shown under the title of the build configuration.

NameWhat it does
reverse.dep.Game_Win64Shipping.platformSets platform in the dependency build of Game_Win64Shipping.
reverse.dep.*.configSets config in every dependency of the chain, at any depth.
reverse.dep.Game_Cook.env.REGIONThe name can be an env. or system. parameter too.

You can set them anywhere a build gets parameters: in the build configuration's own parameters, in parameters it inherits from a project or template, in the Run dialog, and from the API or a trigger. They are not passed to the steps of the build that sets them; they mean nothing there.

Which value wins

  1. A value typed in the Run dialog beats a configured one.
  2. A value for the exact build configuration beats a * value.
  3. A value from a closer build beats one from further up the chain.

A build in the middle of the chain can send values to its own dependencies in the same way.

Two builds ask for different values

A build configuration is built once in a chain. If two builds ask one dependency for different values at the same rank, the chain is not started. The Run dialog says which builds asked for what, and the API answers with the same text.

The target has no such parameter

The value is added to that build as a plain build parameter. The Run dialog shows a warning, so a typo is seen before you run. A name that matches no dependency of the chain is ignored, with a warning in the Run dialog and one line in the build log.

References in a value

A value may hold %name% references, such as %game.version%-%build.number%. The build that sends the value fills them in from its own parameters, once, before it passes the value on. A value that came from another build is not filled in again. A reference that names nothing stays as written, with a warning. A reference to a secret makes the value a secret. The Run dialog shows the result next to the value, for example → 1.4-57.

Reuse, re-run and secrets

  • A finished dependency build is used again only if it ran with the same values. Otherwise a new build starts.
  • A password parameter can be passed down. It stays masked everywhere and is left out of that comparison, so a changed secret alone does not start a new build.
  • Re-run passes the same values again. Re-run with changes lets you change them in the Run dialog.

Up the chain: dep

A build can read what the dependency builds of its own chain used. %dep.<ID>.<name>% is the value used by the dependency build of that build configuration, the reused one or the one started for the chain. Any build of the chain below can be named, not only direct dependencies.

ReferenceValue
%dep.Game_Win64Shipping.build.number%The build number.
%dep.Game_Win64Shipping.build.id%The build id.
%dep.Game_Win64Shipping.build.vcs.number%The changelist or commit.
%dep.Game_Win64Shipping.build.result%SUCCESS, FAILURE and so on.
%dep.Game_Win64Shipping.platform%Any parameter of that build, also one the chain sent it.
%dep.Game_Win64Shipping.STEAM_BUILD_ID%An output a step of that build published.

A reference that names no dependency or no value stays as written, and the build log says so once. A secret is never written into a script. A value that someone who may not configure the build configuration typed is not written into a script either, as for the build's own parameters.

Shell and Batch steps also get environment variables DEP_<ID>_<NAME>: the ID and the name in capitals, dots as underscores. For example DEP_GAME_WIN64SHIPPING_BUILD_NUMBER and DEP_GAME_WIN64SHIPPING_PLATFORM. Only names that fit an environment variable are given, and no secrets.

Where you see it

  • Run dialog, Dependencies tab. Each dependency lists the values it will get and where each came from. Type over a value for this run, or use Add a value for a dependency to pick the dependency and the parameter. Problems show before you run.
  • Parameters of a build configuration. A name that starts with reverse.dep. shows who receives it, and the name field suggests IDs and parameters.
  • Parameters of a dependency build. A value that came from another build says Set by Release build #57, with a link.
  • Build Chains. Each box lists the values it received.
  • Queue. A waiting dependency says Started for Release build #57 with platform=PS5.
  • Build log. The build that sends values has one line for each dependency. Secrets are masked.

From the API

curl -X POST "http://buildspawn/job/Game/job/Release/buildWithParameters?reverse.dep.Game_Win64Shipping.platform=PS5"

This works for a build configuration with dependencies even when it has no parameters of its own. If two dependents ask for different values, the answer is 409 with the text of the problem.

Things to know

  • A Pipeline job can be a member of a chain: the dependencies page and the chain planner work for every kind of job. It receives the values as its parameters (params.NAME) and the DEP_<ID>_<NAME> variables in its environment. %dep.…% references are read in the fields and scripts of build steps, not inside Pipeline code.
  • A personal build of the top build sends and reads values like any other build. A personal build of a dependency is never reused by a chain: the chain builds its own.
  • A composite build receives values, sends them on to its own dependencies and reads %dep.…% in the same way.
  • A Matrix block reads %dep.…% and DEP_… in the steps of every combination, on this machine and on separate machines.
  • %build.number% in a value a build sends is that build’s real number. The number is taken when the chain is planned and the build gets exactly it. If the sending build never runs (cancelled, or reused), the number is left unused, so a gap can show.
