Parameters

Parameters are named values your steps can use. You set them once on a build configuration or a project, and you can change them each time you run a build.

A parameter has a name, a value, a kind and a value type. The kind decides where the value goes: into %name% references, into the environment of every step, or to your build tools. The value type decides what people can type in the Run dialog: free text, a checkbox, a list or a password.

The Parameters tab

Every build configuration has its parameters on Settings › Parameters. Projects have the same page in their settings, and what a project defines passes down to everything inside it.

The table has these columns:

ColumnWhat it shows
NameThe name, with its prefix (env. or system.) if it has one.
ValueThe default value. Passwords always show as dots.
KindConfiguration, Environment or System. See The three kinds.
Defined inThis job, or the project it comes from.
When it is setAsked when the build runs (people can change it in the Run dialog) or Fixed value, and the value type.

Use the chips All, Configuration, Environment and System to filter the list, or type in Search parameters. Press / to jump to the search box.

The Parameters tab saves as you work. There is no Save button: when you close the parameter dialog with Save, the change is stored.

The three kinds

The kind is part of the name. You pick it in the dialog, and Buildspawn adds the prefix for you.

KindNameWhere the value goes
ConfigurationNAMERead in steps and runner fields as %NAME%.
Environmentenv.NAMEPassed to the process of every step as the environment variable NAME. A step can override it for itself.
Systemsystem.NAMEPassed to build tools, for example to Maven as -DNAME=value. Not put in the process environment.

Configuration parameters

A configuration parameter is the everyday kind. Write %CONFIG% in a runner field or in a script, and Buildspawn puts the value there when the build runs. For example, the Windows Build passes its build type to a script like this:

powershell -File Build\ci.ps1 -Stage compile -Platform Win64 -Config %CONFIG%

The script editor helps you: type % and it lists the parameters of the build. A name it does not know gets a hint. See The script editor.

env. parameters

An env. parameter becomes an environment variable. Name it env.UE_SDK_ROOT and every step sees UE_SDK_ROOT. Use this for tools that read their settings from the environment.

rem In a batch step
echo SDK is in %UE_SDK_ROOT%

# In a shell step
echo "SDK is in $UE_SDK_ROOT"

system. parameters

A system. parameter is a property for build tools. Maven steps get it as -D. Other steps don't see it in their environment, but you can still read it as %system.NAME% in a field.

Add or edit a parameter

  1. Open the build configuration and go to Settings › Parameters.
  2. Click Add parameter, or Edit on a row.
  3. Type the Name. Don't type the prefix: choose the Kind instead. Names must be unique in a build configuration.
  4. Choose the Value type and fill in the value (see below).
  5. Optional: open Customize the run dialog to set the label, description and display.
  6. Click Save.

Customize the run dialog

SettingWhat it does
DisplayNormal shows the field. Hidden leaves it out of the Run dialog. Prompt makes the Run button open the Run dialog every time, so people must look at the value.
LabelShown in the Run dialog in place of the name.
DescriptionShown under the field in the Run dialog.
Read-onlyThe configured value is always used. Nobody can change it when they start a build.

Hidden is not protection. Anyone who can read the build configuration can still see the value. Use a password parameter for secrets.

The rules of a parameter count everywhere a build can start: the Run dialog, a trigger, the REST API and the command line. A value that breaks the rules is refused, and the build does not start.

Inheritance

Parameters pass down. A parameter defined on a project reaches every project and build configuration inside it. Parameters on the Root project reach the whole server. See Projects.

An inherited row shows its project in Defined in, and its menu offers:

  • Override: give this build configuration its own default value and description. The name stays the same. The row then says Own, overrides <project>.
  • Disable: this build configuration does not get the parameter. The row says Disabled in this job.
  • Reset: drop your override or your disable and take the parameter back as the project defines it.

If two levels define the same name, the nearest one wins: the build configuration beats its project, and a project beats its parent.

Put values that many build configurations share on the project: the SDK version, the store branch, the Perforce stream. Then you change them in one place.

Built-in parameters

Buildspawn also gives every build parameters you don't need to define, such as %build.number%. Every value is listed in Build values. Values about the checked-out code, such as %build.vcs.number%, are also in Version control parameters. Tools have %tool.<id>%, the path of a tool on the agent.

Tips

  • Use upper case for names that become environment variables, so scripts read them the same on Windows and Linux.
  • A step can set a parameter for the steps after it. See Set parameters from a build.
  • In the visual editor, parameters are one group wired into the build configuration block, and each parameter lists the steps that use it.
