Snapshot and artifact dependencies

How one build configuration needs another: to build first, and to pass files on.

When to use them

Use a snapshot dependency when a build needs another build of the same code to run first: the game needs the engine package. Use an artifact dependency when a build needs files that another build made: the installer needs the cooked content. Together they make a build chain.

How to set them up

  1. Open the build configuration and go to Settings › Dependencies.
  2. Under Snapshot Dependencies click Add snapshot dependency. Under Artifact Dependencies click Add artifact dependency.
  3. Type the build configuration. Start typing a name, such as Engine/Windows Package. It is a path relative to this build configuration's project (.. goes up a project, a leading / starts at the top). The suggestions list every build configuration you can see.
  4. Set the options below and click Save.
  5. Click See the dependency graph to check the chain.

Snapshot dependency: every field

Starting this build configuration starts the ones it depends on first, in parallel when they are independent, and waits for them. All builds of a chain use the same revision of the code.

What a suitable build is

  • it succeeded (when the dependency only uses successful builds), and was started after the dependency's configuration was last saved;
  • it used the same parameter values the chain requests (the dependency's default values, with any reverse.dep values applied);
  • it is the dependency's newest build: no newer build is running or queued;
  • the builds of its own snapshot dependencies are reused too.

Run… on the build configuration can rebuild failed and incomplete dependencies, or all of them, whatever these options say.

A Pipeline copies the files when the script calls resolveArtifactDependencies() inside node { … }. The step fails the build when an artifact cannot be resolved.

Dependency options

Three switches at the bottom of the Dependencies page say how this build configuration behaves while the ones around it are building. Click Set up (or Edit) on a card, turn it on and save.

SwitchWhat it doesDefault
Wait while an upstream build configuration is buildingThis build configuration does not start while a build configuration it depends on is building or waiting in the queue. The card shows what is building now.Off
Wait while a downstream build configuration is buildingThis build configuration does not start while a build configuration that follows it is building or waiting in the queue.Off
Keep the build logs of dependenciesWhile a build of this build configuration is kept, the builds it used from other build configurations are kept too, so their logs stay readable.Off

A worked example

The Game/Installer build has a snapshot dependency on Game/Cook Content and an artifact dependency on it: Build from the same chain, rule Cooked/**/* => Content, clean on. Starting the installer starts the cook (or reuses a suitable one), then copies its files into Content.

What you see when it runs

The queue shows the dependency waiting for the build that started it. The Build Chains page shows the graph. The console of the installer lists the artifact files it copied. See Use another build's artifacts.

Problems and fixes

ProblemWhat to do
Enter at least one artifact ruleType a rule such as target/*.jar => lib.
The target path must be relative to the workspace and must not contain ..Remove the .. and the drive letter.
Build from the same chain is refusedAdd a snapshot dependency on the same build configuration first.
A re-run says the source build no longer existsThe build whose artifacts the first run used was deleted. The re-run does not copy other artifacts instead.
A new build starts every timeThe dependency ran with other parameter values, or is older than its last configuration change. See "What a suitable build is".
