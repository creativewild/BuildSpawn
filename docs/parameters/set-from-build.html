Set parameters from a build

A step can change a parameter while the build runs. It prints one special line, and the steps after it get the new value.

This is useful when one step works something out that later steps need: the version number from a file, the name of a package, the folder an engine was unpacked to. You don't need files or scripts to pass it along. You print a service message: a line that starts with ##buildspawn. Buildspawn reads it from the step's output.

The ##buildspawn message

The message looks like this:

##buildspawn[setParameter name='NAME' value='VALUE']

The name decides what the value becomes:

NameWhat the later steps get
versionA build parameter. Later steps read it as %version% in their fields and scripts. It is not put in the environment.
env.GAME_VERSIONAn environment variable GAME_VERSION in the process of every later step.
system.versionA property for build tools, as with system. parameters.

If the build already has a parameter with that name, the new value replaces it for the steps after this one. The build log says so, for example setParameter version replaces the build parameter version for the steps after this one.

Rules

  • The name starts with a letter or _, and holds letters, digits, ., _ and -, up to 100 characters.
  • The value can be up to 8,192 characters. A build keeps at most 200 values set this way.
  • Only the output of a running step's own script counts. A message that comes from elsewhere in the log, or after the step has ended, is refused with a line in the log.
  • If the same name is set twice, the later value wins.
  • The value reaches the steps after the one that printed it, not the rest of the same step.

Special characters

Values are in single quotes. To put a quote or a line break in a value, escape it with |:

You wantWrite
'|'
|||
A new line|n
A carriage return|r

Names a step may not set

Some environment variables change which programs run or how they start. To keep builds safe, a step cannot set these as env. names:

  • search paths and loaders: PATH, PATHEXT, LD_PRELOAD, LD_LIBRARY_PATH, LD_AUDIT, and every DYLD_* name;
  • shell start-up: BASH_ENV, ENV, PROMPT_COMMAND, COMSPEC, PSMODULEPATH;
  • tool options: JAVA_TOOL_OPTIONS, _JAVA_OPTIONS, JDK_JAVA_OPTIONS, NODE_OPTIONS, NODE_PATH, PYTHONPATH, PYTHONSTARTUP, PYTHONHOME, PERL5OPT, PERL5LIB, RUBYOPT, RUBYLIB;
  • .NET profilers and start-up hooks: DOTNET_STARTUP_HOOKS and the COR_* and CORECLR_* profiler names;
  • every GIT_* name.

Upper and lower case count the same. A refused name gets a line in the build log that says why. Plain names and system. names never touch the environment, so they are never refused.

An administrator can lift the block: Settings › System, section Build steps, tick Let build steps set any environment variable.

Only lift the block if you trust everyone who can change the scripts your builds run. A step that sets PATH decides which programs all later steps run.

Examples

Pass a version to later steps

A first step reads the version from the project and prints it. A batch step:

for /f %%v in (Build\version.txt) do echo ##buildspawn[setParameter name='version' value='%%v']

A PowerShell step does the same:

$v = (Get-Content Build\version.txt).Trim()
Write-Host "##buildspawn[setParameter name='version' value='$v']"

A later step uses it in its command:

powershell -File Build\ci.ps1 -Stage package -Version %version%

Set an environment variable

echo "##buildspawn[setParameter name='env.ENGINE_DIR' value='$(pwd)/Engine']"

Every later step now has ENGINE_DIR in its environment.

A value with a quote in it

echo "##buildspawn[setParameter name='title' value='Skyforge: the dragon|'s path']"

For how to read the values, see Parameter references. For the other messages, see Service messages.

Step outputs

A step can also declare its outputs: a name and a type (Text, Number, True/false or File). The step must then set each output with a setParameter message. A step that ends without setting a declared output fails with did not set output <name>. In the visual editor, outputs become typed wires to the steps that read them.

Values set by steps also carry over when you resume a build from a later step, and from the steps of parallel blocks that run on separate machines.

Other service messages

A build can report a number for the Statistics tab of its build configuration:

##buildspawn[buildStatisticValue key='shaderCount' value='12840']

The key holds letters, digits, ., - and _; the value must be a number. The full list of messages, including the ::group:: lines for the build console, is in Service messages.
