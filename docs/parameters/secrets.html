Secrets and Vault

Keep passwords, keys and tokens out of sight: in settings, in the Run dialog and in build logs.

Buildspawn has two ways to give a build a secret:

  • a password parameter, stored encrypted on the server;
  • a Vault reference, fetched from HashiCorp Vault when the build starts and never stored at all.

Either way, Buildspawn masks the value in the build log, so a script that prints it by accident shows dots instead.

Secret parameters

A password parameter is a normal parameter with the value type Password.

  1. Open the build configuration or project and go to Settings › Parameters.
  2. Click Add parameter.
  3. Type a name, for example STEAM_UPLOAD_KEY, and pick a Kind. Pick Environment variable (env.) if your script reads the secret from the environment.
  4. Set Value type to Password and type the value.
  5. Click Save.

After you save:

  • The value is stored encrypted and is never shown again, not even to you. The table shows dots.
  • When you edit the parameter, the field says Stored. Leave empty to keep it. Type a new value only to replace it.
  • In the Run dialog the field shows Concealed with a Change Password button. People can give a different value for one build without seeing the stored one.
  • People who may only view the settings never receive the value. It is masked in the visual editor and in project parameters too.

Use a secret in a script

Buildspawn never writes a secret into the text of a script, even if you write %STEAM_UPLOAD_KEY%. Read it from the environment instead:

rem Batch
upload-tool --key "%STEAM_UPLOAD_KEY%"

# PowerShell
upload-tool --key $env:STEAM_UPLOAD_KEY

# Shell
upload-tool --key "$STEAM_UPLOAD_KEY"

In a batch file, %NAME% is the batch file's own syntax for an environment variable, so the value is read when the script runs, not written into it.

Masking hides the exact value. It cannot hide a secret that your tool changes before it prints it, for example base64-encoded or split over lines. Don't print secrets on purpose.

Credentials

Runner fields that need a secret, such as a NuGet API key, a Unity licence or a Perforce password, take a credential ID, never the value itself. Buildspawn looks up the credential when the build runs, with the rights of the build configuration. Credentials are kept in the project's Credentials page or at server level.

Vault references

If your studio keeps secrets in HashiCorp Vault, builds can fetch them when they start. The value is never saved in Buildspawn.

1. Add a Vault connection

A connection tells Buildspawn where Vault is and how to sign in. Add it on a project, and every project below it can use it. Add it on the Root project for the whole server; see Global connections.

  1. Open the project's settings and go to Connections.
  2. Click Add connection and choose HashiCorp Vault.
  3. Fill in the display name, a connection ID (for example vault), the Vault URL and, if you use one, the namespace.
  4. Choose how to sign in: AppRole (role ID and secret ID), LDAP (user name and password) or GCP IAM.
  5. Click Test connection, then Save.

Both the server and every agent that runs the build must reach Vault. The server signs in; the agent fetches the values.

2a. A Remote parameter

  1. On Settings › Parameters, click Add parameter.
  2. Set Value type to Remote and Source to HashiCorp Vault.
  3. Pick the connection and type the query, for example secret/data/skyforge/store!/upload_key.
  4. Click Test query to check it. The button is shown only to people who can configure the job, and the value found is never displayed.
  5. Click Save.

2b. A reference inside any value

You can also put a reference in the value of any parameter:

%vault:secret/data/skyforge/store!/upload_key%
%vault:studio-vault:secret/data/skyforge/store!/upload_key%

The first form uses the default connection. The second names the connection ID first.

The query

A query is path!/key:

  • path is the secret's path in Vault. Both KV version 1 and version 2 work; version 2 data is unwrapped for you.
  • key picks one field of the secret, for example /password. Without a key, a secret with only one field gives that field.

What happens when a build runs

  1. The server signs in to Vault once per connection and passes a short-lived, wrapped token to the agent.
  2. The agent fetches all the values in one go, keeps them in memory only and masks them in the log.
  3. During a long build the token is renewed. When the build ends, the token is revoked, also after a server restart.

If a value cannot be fetched, the build stops with a problem that says which query failed.

Some tools want to talk to Vault themselves. Add the parameter vault.<connection ID>.set.env with the value true, and the build gets VAULT_ADDR and VAULT_TOKEN in its environment.

People who cannot edit the project cannot change Vault parameters or references when they start a build.

Credentials by kind

Each kind of credential has its fields and its use in steps on Credentials. A password parameter is described on Password parameter.

Tips

  • Put shared secrets on the project, not on each build configuration, so you change them in one place.
  • Hidden in the Run dialog is not a secret. Use Password or Remote.
  • With versioned settings, passwords are left out of the files in the repository and kept on the server.
