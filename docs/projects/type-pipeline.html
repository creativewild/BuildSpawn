Pipeline

A Pipeline is a build written as a script. The script, typed in Buildspawn or kept as a file in version control, defines stages, parallel work and approvals.

When to use it

Use it when your team already writes build logic in code, or when the build needs branching logic that is hard to draw as a list of steps. For most game builds a build configuration is easier to read and edit. A Pipeline needs someone who can write Groovy.

How to set it up

  1. Open the project and click New Item. Type a name.
  2. Under Type choose Pipeline. Click Create.
  3. On Settings open the Pipeline tab. Under Definition choose Pipeline script (the script is written here) or Pipeline script from SCM (the script is a file in version control).
  4. Fill in the fields of the definition (see the tables). Leave Use Groovy Sandbox on if you can.
  5. Click Save, then Run.

Other tabs of a Pipeline

  • General, Build Triggers and Parameters work as on a build configuration. Concurrent builds can also abort the running build when a newer one starts.
  • Build Steps shows the stages read from the text of the script. It does not edit them and it does not run the script. A Pipeline from SCM shows only where the file is, because it is read when a build starts.
  • Run behaviour in Workspace options: resume after a restart, durability and stashes.
  • The Visual editor can edit declarative Pipelines. See Canvas and palette.
  • A template gives a Pipeline only its parameters.

The sandbox and script approval

The Groovy sandbox lets a script call only methods that an administrator has approved. If the script calls something else, the build fails with Scripts not permitted to use method .... An administrator opens Script approval in the global settings, reads the pending signature and approves it, or removes it. If you turn the sandbox off, the whole script needs approval by an administrator, unless you are one. Keep the sandbox on, and keep the script small.

Never approve a signature you do not understand. An approved signature is allowed for every sandboxed script on the server, not only this Pipeline.

A worked example

The studio keeps ci/build.pipeline in the Git repository of the launcher. Definition is Pipeline script from SCM, SCM is Git with the repository address and the credential, Script Path is ci/build.pipeline. The file has three stages: Build, Test and Package. See the how-to Make a Pipeline from a script.

pipeline {
  agent any
  stages {
    stage("Build")   { steps { bat "build.bat" } }
    stage("Test")    { steps { bat "test.bat" } }
    stage("Package") { steps { bat "package.bat" } }
  }
}

What you see when it runs

The build page shows the stages as a graph, with the result and time of each. The console log is one block per step. The History tab lists the builds, as for a build configuration. Failed builds can be replayed or restarted from a stage.

Problems and fixes

ProblemWhat to do
Scripts not permitted to use method ...The sandbox blocked a call. Ask an administrator to approve the signature, or change the script.
Waiting for approvalYou turned off the sandbox and are not an administrator. Turn it on again, or ask for approval.
Script file not foundThe Script Path is wrong, or the branch has no file. Check the path and the branch of the SCM.
A step of the Build Steps tab cannot be editedPipeline steps are in the script. Edit the script or the file in version control.
