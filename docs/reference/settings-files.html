Settings files

One small text file holds how the server starts: its port, memory, folders and Java options.

Windows uses buildspawn.cfg. Linux and macOS use buildspawn.conf. They hold the same settings with slightly different names. Everything else, such as projects, users and agents, lives in the home folder and is set in the web interface.

You rarely need to open the file by hand. These all edit it for you and keep your comments:

  • the Settings tab of the Windows app (see The Windows app);
  • the Settings view (7) of the terminal program;
  • buildspawn set key=value (see Terminal program commands; its key for the data folder is home).

Restart Buildspawn after you change the file. The server reads it only when it starts.

The Windows app, the Windows service and the terminal program all read the same file, so they never disagree. The last line of buildspawn help shows which file this copy uses, and buildspawn check prints the full Java command made from it.

buildspawn.cfg (Windows)

One key=value per line. Lines that start with # are comments.

KeyDefaultWhat it does
port8080The web port.
listenallall: every network interface. localhost: this computer only.
memorya quarter of the computer's memory, between 2g and 16gThe Java heap, used as both the start and the largest size, for example 4g.
java-optionsthe recommended set (below)Extra Java options.
datasee Where the file isThe home folder: projects, build history and settings.
logssee Where the file isbuildspawn.log, gc.log and heap dumps.
argumentsemptyExtra Buildspawn arguments, for example --sessionTimeout=480.

In java-options, data and logs you can use placeholders:

PlaceholderStands for
{install}The program folder
{data}The home folder
{logs}The logs folder

An example:

# Buildspawn settings
port=8080
listen=all
memory=8g
data={install}\data
logs={install}\logs
arguments=--sessionTimeout=480

Folders named in the Java options are created before Java starts. Keys that this version doesn't know are kept as they are.

An installed copy keeps its file in C:\ProgramData, which only administrators can change. The Windows app asks for permission when you save.

buildspawn.conf (Linux and macOS)

The file uses shell syntax: KEY=value, or KEY="value with spaces". Lines that start with # are comments.

KeyDefaultWhat it does
BUILDSPAWN_PORT8080The web port.
BUILDSPAWN_LISTENallall: every network interface. localhost: this computer only.
BUILDSPAWN_MEMORYemptyThe Java heap, for example 4g. Empty means a quarter of the computer's memory, between 2 GB and 16 GB.
BUILDSPAWN_HOME"{install}/data"The home folder: projects, build history and settings. The packages use /var/lib/buildspawn.
BUILDSPAWN_LOGS"{install}/logs"gc.log, heap dumps, and buildspawn.log when the server runs in the background. The packages use /var/log/buildspawn.
BUILDSPAWN_JAVA_OPTIONSthe recommended set (below)Java options.
BUILDSPAWN_ARGUMENTSemptyExtra Buildspawn arguments, for example --sessionTimeout=480.

{install} is the program folder. In the Java options and arguments, {home} and {logs} stand for those folders.

An example:

# Buildspawn settings
BUILDSPAWN_PORT=8080
BUILDSPAWN_LISTEN=all
BUILDSPAWN_MEMORY=8g
BUILDSPAWN_HOME="/srv/buildspawn"
BUILDSPAWN_LOGS="{install}/logs"
BUILDSPAWN_ARGUMENTS=--sessionTimeout=480
  • To use another file, set BUILDSPAWN_CONFIG=/path/to/file before you run bin/buildspawn.
  • With the Linux service, a home folder outside the default must belong to the buildspawn user: sudo chown -R buildspawn:buildspawn /srv/buildspawn.
  • Package upgrades keep this file.

The recommended Java options

A new settings file starts with this set. It is tuned for a build server that runs for weeks at a time.

-XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:+UseStringDeduplication -XX:+ParallelRefProcEnabled --enable-native-access=ALL-UNNAMED -XX:+ExplicitGCInvokesConcurrent -XX:ReservedCodeCacheSize=512m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath={logs} -XX:+ExitOnOutOfMemoryError -Xlog:gc*:file={logs}/gc.log:time,uptime:filecount=10,filesize=50M -Djava.awt.headless=true
OptionWhy
-XX:+UseG1GC, -XX:MaxGCPauseMillis=200A memory cleaner with short pauses, so pages stay quick.
-XX:+UseStringDeduplicationSaves memory on repeated text, such as job and file names.
-XX:+ParallelRefProcEnabled, -XX:+ExplicitGCInvokesConcurrentKeep memory clean-ups short.
--enable-native-access=ALL-UNNAMEDLets the server use native system calls without a Java warning at start-up.
-XX:ReservedCodeCacheSize=512mRoom for compiled code, so the server stays fast after a long run.
-XX:+HeapDumpOnOutOfMemoryError, -XX:HeapDumpPath={logs}Writes a memory dump to the logs folder if memory runs out, so you can find the cause.
-XX:+ExitOnOutOfMemoryErrorStops the server when memory runs out. The service then starts it again.
-Xlog:gc*:file={logs}/gc.log:...Keeps a memory log, gc.log, in ten files of 50 MB at most.
-Djava.awt.headless=trueThe server has no screen. Charts are drawn without one.

An existing settings file keeps its own options when you upgrade. To pick up the newest set on Windows, click Reset to recommended in the app's Settings tab. On Linux and macOS, add any missing option to BUILDSPAWN_JAVA_OPTIONS yourself, for example --enable-native-access=ALL-UNNAMED, which is new in 1.4.

macOS

The macOS download is a folder, like the Linux tar.gz. It uses buildspawn.conf with the same keys as Linux, in the folder, and keeps data/ and logs/ next to it. Starting at login uses a LaunchAgent, ~/Library/LaunchAgents/io.github.creativewild.buildspawn.plist, which runs bin/buildspawn run as you with this folder's settings file. Its output goes to logs/buildspawn.log. Presets are in ~/Library/Application Support/Buildspawn/presets.json.

The buildspawn.service unitThe systemd service, started and enabled by the package. A unit you make with install-service from a tar.gz folder is written to /etc/systemd/system/buildspawn.service and takes precedence. It runs bin/buildspawn run as the system user buildspawn, with BUILDSPAWN_CONFIG pointing at the settings file, and restarts it after a failure.

Portable markers on Windows

On Windows the app decides where the settings live from the program folder. If a file named portable, or a buildspawn.cfg, is next to Buildspawn.exe, the copy is portable and keeps settings, data and logs in that folder. Otherwise it is an installed copy and uses C:\ProgramData\Buildspawn. An older buildspawn-service.cfg is converted once into buildspawn.cfg (the old file is left as it was). BUILDSPAWN_CONFIG names a different settings file.

Inside the data folder

The data folder (the home) is what you back up. You see these in it:

NameWhat it holds
config.xmlThe main server settings. Most pages of Settings save here or in a file next to it.
Other *.xml files next to itOne file per feature, for example credentials.xml (stored credentials), nodeMonitors.xml, the agent pools and the Perforce settings.
jobs\One folder per project and build configuration: its config.xml, build history, artifacts and its workspace on the server.
users\One folder per user, with their settings, API tokens and preferences such as the theme.
nodes\One folder per agent: its settings.
secrets\The keys that protect saved passwords and credentials. Keep it with the backup. On a new server it also holds initialAdminPassword: the one-time password of the user admin. The file is deleted when you finish the setup page.
secret.key and related filesServer keys. Keep them with the backup.
trust\The trusted certificates: trust.properties (the switches windowsStore and sendToAgents) and added\ with one .pem and one .properties file per certificate, named by its SHA-256 fingerprint. It is kept on upgrades. See Trusted certificates.
plugins\The plugins in use.
war\The unpacked web application. Made again at each start.
userContent\, updates\, fingerprints\, logs\Files you share, update data, build fingerprints and server-side logs of the web application.
buildspawn.pidA lock. It stops two servers from using the same home. It is removed when the server stops.

The server log is separate from the home. buildspawn.log sits in the logs folder from the settings file when Buildspawn runs in the app, in the background or as a Windows service, together with gc.log and any heap dumps.

Agent files

An agent has its own small files. They are not part of the server's backup.

File or folderWhat it is
conf\buildspawn-agent.properties (conf/… on Linux and macOS)The agent's settings: serverUrl (required: the address of your server), name (default: the computer's name), registrationToken (if the administrator asks for one) and workDir (the work folder, default work). After an administrator authorizes the agent, its secret is written to the file, so keep it private. A line with # in front is off.
The work folderWhere builds check out and run. By default work next to the agent, or .buildspawn-agent in the user's home folder when the agent was started without a work folder.
<work folder>\trust\The agent's trusted certificates: trust.properties, added\ (added on this machine) and from-server\ (sent by the server, replaced as a whole each time).

See Install an agent, the agent tray app and the agent terminal program.

Tips

  • Run buildspawn check after a change. It tries the Java options before you rely on them. In the Windows app, Check with Java does the same.
  • If the Windows service stops within seconds of starting, the reason is in the Windows Application event log (source Buildspawn) and in logs\buildspawn.log.
  • Keep listen on localhost while you try Buildspawn out. Switch to all when agents and other people need to reach it.
