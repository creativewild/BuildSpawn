Service messages

Special lines a build prints to talk to Buildspawn: set a parameter, record a number, name the build, set its status, or group the log into blocks.

A service message is a normal line of output. Your script prints it with echo, Write-Host, print or any other command. Buildspawn spots the line while the build runs and acts on it. Any tool that can print text can use them.

There are two families:

FamilyLooks likeUsed for
Buildspawn messages##buildspawn[name attribute='value']Setting parameters, recording statistics, naming the build and setting its status
Log markers::group::NameBlocks, warnings and errors in the build console

Buildspawn messages

Message format

##buildspawn[messageName attribute='value' attribute='value']

A message with one value can leave out the attribute name:

##buildspawn[messageName 'value']
  • The line contains ##buildspawn[, the message name, then attributes, then ].
  • Each attribute is name='value', in single quotes, with a space before it.
  • Spell it exactly like this. Other spellings are ignored.
  • Only the processes a build step starts, while the step runs, can send messages: its script or its tool. The same line anywhere else in the log is refused, with a line that says so.
MessageWhat it does
setParameterSets a value for the later steps.
buildStatisticValueRecords a number to chart across builds.
buildNumberGives the build its name, such as 1.4.212-CL48213.
buildStatusSets the build's status text, and can make its result worse.

Escaping special characters

Inside a value, put a vertical bar | in front of special characters:

WriteTo get
|'a single quote '
||a vertical bar |
|[ and |]square brackets [ and ]
|na new line
|ra carriage return

setParameter

Sets a value for the build steps that come after this one.

##buildspawn[setParameter name='version' value='1.4.212']
Name you useWhat it setsLater steps read it as
versionA build parameter. It is not put into the environment.%version%
env.GAME_VERSIONThe environment variable GAME_VERSION%env.GAME_VERSION%, or $GAME_VERSION / %GAME_VERSION% in a script
system.build.flavourA system property, kept as it is. It is not an environment variable.%system.build.flavour%

From a few common shells:

# Bash
echo "##buildspawn[setParameter name='env.GAME_VERSION' value='1.4.212']"

# PowerShell
Write-Host "##buildspawn[setParameter name='env.GAME_VERSION' value='1.4.212']"
Write-Host "##buildspawn[setParameter name='package' value='$($zip.FullName)']"

# Windows batch
echo ##buildspawn[setParameter name='env.GAME_VERSION' value='1.4.212']

# Python
print("##buildspawn[setParameter name='env.GAME_VERSION' value='1.4.212']")

The rules:

RuleDetail
Who can set valuesOnly the processes a build step starts, while the step runs: its script or its tool. The same line anywhere else in the log is refused, for example in a commit message or after the step ended.
NamesStart with a letter or _. Then letters, digits, ., _ and -. 100 characters at most.
Values8,192 characters at most.
How many200 values per build at most.
Same name as a build parameterThe new value replaces it for the later steps. The log says so once for each name.
Blocked environment namesNames that change which programs run or how they start are refused, for example PATH, LD_LIBRARY_PATH, PYTHONPATH, NODE_OPTIONS, JAVA_TOOL_OPTIONS, and every DYLD_* and GIT_* name. An administrator can allow them with Let build steps set any environment variable in the system settings.
RefusalsEach refused message gets a line in the build log that says why.
Resumed buildsA build that resumes from a later step keeps the values the earlier steps set.

A step can also declare outputs in the step editor. Each output must then be set with setParameter before the step ends. See Set parameters from a build for worked examples.

buildStatisticValue

Records a number for this build, such as code coverage, a package size or a load time. Buildspawn charts it across builds on the build configuration's Statistics tab, where you can add custom charts.

##buildspawn[buildStatisticValue key='coverage' value='81.5']
AttributeRule
keyThe name of the number. Letters, digits, ., - and _, 100 characters at most.
valueA number, for example 12, -3.5 or 1.2e6.
  • If a build reports the same key twice, the last value counts.
  • A build keeps 200 keys at most.
  • A line with a bad key or a value that isn't a number is ignored.
# PowerShell: report the size of the Windows package in megabytes
$mb = [math]::Round((Get-Item Build\Game-Win64.zip).Length / 1MB, 1)
Write-Host "##buildspawn[buildStatisticValue key='package.win64.mb' value='$mb']"

# The same in Bash
size=$(du -m Build/Game-Win64.zip | cut -f1)
echo "##buildspawn[buildStatisticValue key='package.win64.mb' value='$size']"

buildNumber

Gives the build its name. The name shows on the build page, in the History tab and on chain pages. The build number itself, its address and its links stay the same.

##buildspawn[buildNumber '1.4.%build.counter%-CL48213']

References in the name are filled in as in the build number format on Settings › General, and a few more:

WriteTo get
%build.counter%The build number, for example 212.
%name%A build parameter, or a value an earlier step set with setParameter.
%build.vcs.number%, %build.triggeredBy.username% and the other build valuesThe changelist or commit, who started the build, and so on. See Values a script can read.
{build.number}The build's name so far, to add to it.
%%One percent sign.
 
# PowerShell: name the build after the version and the changelist
Write-Host "##buildspawn[buildNumber '1.4.%build.counter%-CL%build.vcs.number%']"

# ... or after a value the script worked out
$cl = (p4 -p $env:P4_PORT -u $env:P4_USER -P $env:P4_TICKET changes -m1 "//depot/game/main/...#have") -replace '^Change (\d+).*','$1'
Write-Host "##buildspawn[buildNumber '1.4.%build.counter%-CL$cl']"
  • If a step sends it more than once, the last name counts.
  • A name that refers to an unknown parameter or to a password is refused. The build keeps its name and the log says why.
  • 200 characters at most.

buildStatus

Sets the build's status text: the short line next to the result on the build page and in the History tab, such as Success or Tests passed: 120.

##buildspawn[buildStatus text='Uploaded to store branch qa' status='SUCCESS']
AttributeRule
textThe new status text, 500 characters at most. {build.status.text} in it stands for the text the build would show anyway, so text='{build.status.text}, uploaded' gives Tests passed: 120, uploaded.
statusOptional: SUCCESS, UNSTABLE or FAILURE. It is applied when the build ends. It can only make the result worse, never better: a failed build stays failed even if a script sends SUCCESS.
 
# PowerShell: say where the build went, and mark it unstable if the upload was partial
if ($uploaded -lt $total) {
  Write-Host "##buildspawn[buildStatus text='Uploaded $uploaded of $total depots' status='UNSTABLE']"
} else {
  Write-Host "##buildspawn[buildStatus text='{build.status.text}, uploaded to store branch qa']"
}

The last text a build sends counts. The status text shows once the build has finished. A text that holds a password parameter's value is refused.

Keeping files a script names

To keep files whose path a script works out, set it with setParameter as an environment value and use it in the artifact pattern on Settings › General: the script sends ##buildspawn[setParameter name='env.PACKAGE_DIR' value='out\build\1.4.212'] and the pattern is ${PACKAGE_DIR}\*.zip => builds.

Log markers

Log markers shape how the build console shows your output. Each marker is a line of its own, at the start of the line. Spaces before it are allowed.

MarkerWhat it does
::group::NameStarts a block called Name. Blocks can sit inside other blocks.
::group::Name::DetailsStarts a block and shows Details after the name in its header, for example a count.
::endgroup::Ends the innermost open block.
::endgroup::STATUSEnds the block and says how it ended: SUCCESS, UNSTABLE, FAILURE, ABORTED or SKIPPED.
::warning::TextShows Text as a warning. It counts in the console's warning total.
::error::TextShows Text as an error. It counts in the console's error total.
 
echo "::group::Cook content::Win64"
UnrealEditor-Cmd.exe Game.uproject -run=cook -targetplatform=Windows
echo "::endgroup::"

echo "::group::Compile shaders"
build-shaders --platform win64 || echo "::warning::Shader cache was rebuilt from scratch"
echo "::endgroup::SUCCESS"

echo "::error::Missing texture: Content/Props/Crate_D.uasset"

The same in PowerShell:

Write-Host "::group::Cook content::Win64"
& UnrealEditor-Cmd.exe Game.uproject -run=cook -targetplatform=Windows
if ($LASTEXITCODE -ne 0) { Write-Host "::error::Cooking failed with exit code $LASTEXITCODE" }
Write-Host "::endgroup::"

Write-Host "::warning::Shader cache was rebuilt from scratch"

The plain text log stays readable: the marker line shows as the block name, or as the warning or error text.

Values a script can read

The complete list of references and environment variables is on Build values.

Besides your own parameters, every step can read these:

ParameterEnvironment variableWhat it holds
%build.counter%, %build.number%BUILD_NUMBERThe build number.
%build.triggeredBy.username%BUILDSPAWN_TRIGGERED_BYThe user ID of whoever started the build. For a build another build started, the user who started the first one, when known. Empty for a schedule or a version control trigger.
%build.vcs.number%BUILD_VCS_NUMBERThe changelist or commit the build used.
%build.checkoutDir%WORKSPACEThe checkout folder on the agent.
%agent.hostname% and the other agent.* valuesAbout the agent the build runs on.
P4_PORT, P4_USER, P4_CLIENT, P4_TICKETIn a build with a Perforce root: its server, user, workspace and a login ticket, so p4 -p $env:P4_PORT -u $env:P4_USER -c $env:P4_CLIENT -P $env:P4_TICKET changes -m1 //... works with no password in the script.
 
# PowerShell: who started the build
Write-Host "Started by $env:BUILDSPAWN_TRIGGERED_BY"
if ("%build.triggeredBy.username%" -eq "") { Write-Host "Started by a schedule or a check-in" }

Tips

  • Close every ::group:: with ::endgroup::. Otherwise the output that follows lands inside the open block.
  • Never print a secret in a message. The line is part of the build log like any other.
  • Prefer env.NAME only when a later tool needs an environment variable. A plain build parameter is safer and shows up in %name% references.
  • If a value seems missing, search the build log for the message. A refusal line next to it says why.
