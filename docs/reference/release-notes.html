1.9.3

Build 2.589-buildspawn.21. Install it over 1.9.2, 1.9.1, 1.9 or 1.8.

Fixes

  • Resume from a step works with Perforce. Before, resuming a build of a build configuration with a Perforce root failed at its first step with a NullPointerException. The source records taken over from the failed build (the changelist, the credential and the login ticket) now belong to the resumed build. Git roots that tag builds are fixed the same way. See Resume a build.

Checked

  • 12 resume tests, including a new one for this case.
  • The server starts with no SEVERE lines in its log. Every agent download was compared with the tools built for it.
  • The Linux and macOS packages passed their package test with 0 failures.

1.9.2

Build 2.589-buildspawn.20.

Security

  • Script Security 1436.1438.v3dc5ef7d16f2-buildspawn fixes a sandbox bypass through a partly written @Builder annotation name (SECURITY-4278).
  • Pipeline: Groovy 4403.4405.va_b_cdb_b_d0b_89f-buildspawn fixes a sandbox bypass through field values in interfaces (SECURITY-4152).
  • The notice Warnings have been published for these two goes away.

Agents

Download the agent again from the server (New agent page) or copy the new files over the agent folder. The agent's settings and registration (conf\buildspawn-agent.properties) do not change.

  • Windows tray app (bin\Buildspawn Agent.exe): the Certificates tab is there. In 1.9 and 1.9.1 the agent download still carried the old tray app without it, although the agent did receive the server's certificates. The old tray app could also fail to start on some machines; this one starts. When the tray starts the agent, what the agent prints goes to logs\run-agent.log, and unexpected errors of the tray app go to logs\tray.log.
  • Terminal screen (buildspawn-agent-tui, every system): a new view 8, Certificates, shows the certificates from the server and the ones added on that machine. You can add a certificate file, remove one, see its details, switch the Windows certificate store and restart the agent. A new command buildspawn-agent-tui certs list | add FILE | remove FINGERPRINT-OR-NAME | windows-store on|off is for machines without a screen.
  • Windows service: the download now includes the service definition (bin\buildspawn-agent-service.xml). Without it the service wrapper stopped with only Unhandled exception in the event log and no log file. install-service.bat can be run again on a machine where the service exists, for example after moving the agent folder. uninstall-service.bat and stop-agent.bat also work when the service definition is missing.

Checked

  • Every agent download was opened and compared with the tools built for it: tray app, terminal screen and service files.
  • The server starts with 0 SEVERE lines. The Linux and macOS packages passed their test with 0 failures (64 checks).

1.9

Build 2.589-buildspawn.18.

Trusted certificates

Trust your company's root certificate authority without editing Java's own certificate file. The certificates you add are kept when you upgrade.

  • Server: Settings › Security › Trusted certificates (administrators only). Paste Base64 text, or choose a .pem, .crt, .cer, .der or .p7b file. Check the preview, then add. Each certificate shows its name, issuer, validity and SHA-256 fingerprint, with badges for root, intermediate, not a CA, expired and already trusted. Private keys are refused and never kept.
  • Also trust Windows' certificate store covers roots your IT team pushes with group policy.
  • Send these to agents (on by default) passes the certificates to every agent, which uses them after it restarts. A table shows which agents are up to date.
  • A notice appears 30 days before an added certificate expires. Changes take effect after a restart, and the page tells you when one is needed.
  • Windows app (Buildspawn.exe): a new Certificates tab with the same Add dialog and Restart now.
  • Agent tray app: a new Certificates tab with From the server and Added on this machine.
  • Terminal program: buildspawn certs list | add FILE | remove FINGERPRINT-OR-NAME | windows-store on|off.

Build scripts

  • Set the build's name: a step prints ##buildspawn[buildNumber '1.4.2-CL%build.vcs.number%']. The last name printed wins.
  • Set the status text: ##buildspawn[buildStatus text='{build.status.text}, uploaded to Steam branch qa']. The text shows on the build page and in History. status= can only make the result worse, never better. See The build name and status text.
  • New build value: %build.triggeredBy.username% (environment variable BUILDSPAWN_TRIGGERED_BY) holds the user who started the build. It follows chains and retries.
  • The guide's Service messages page lists every log command and build value, with PowerShell examples.

Look and feel

  • Resizable sidebar: drag the right edge of the left sidebar, from 200 pixels to half the window. Your width is remembered in your browser. Double-click the edge to reset it. With the keyboard, press Tab to the edge, then use the arrow keys (Shift for bigger steps).
  • No more NEW badges on pages. Spaces are fixed in the paused/archived banner and in the project list.

Fixes

  • Parameters table: the columns fit the card at every desktop size and Windows scaling, also with a wide sidebar. The Edit button stays inside the card, headings stay on one line, and long values end in … with the full text on hover.
  • Deleting a template: Delete on a template's page works again; in 1.8 it showed Page not found. If build configurations use the template, they are detached first and each keeps a copy of its settings. The confirmation says how many. If you may not change one of those build configurations, nothing changes.
  • Visual editor: opening a node's properties no longer shows an empty dialog with no Close button (a 1.8 bug).
  • Fewer log warnings: visits from people who are not signed in no longer write a WARNING with a stack trace. Real errors still do.
  • Security page saves completely: switching the sign-in method, for example to Entra ID, now saves the whole page. Before, the settings after the switch could be lost.

Agents need 1.9 or newer to receive trusted certificates from the server. Older agents are listed as Older agent.

1.8

Build 2.589-buildspawn.17.

Store uploads

  • Steam. Build steps in the Store group: Steam upload (app and depots, file mappings, file properties, the build description and the branch to set live), Steam: set branch live, Steam: check build, Steam: DRM wrap, Steam: workshop item and Install SteamCMD. The account is a Steam build account credential, with Steam Guard handled for you. The steps preview the generated build script, and the log hides secrets. Setting a branch live needs its own permission, in Pipeline as well.
  • Epic Games Store. Epic Games Store upload, Epic: label binary, Epic: inspect binaries, Epic: copy binary, Epic: optimise patch, Epic: download binary, Epic: delete binary and Install BuildPatch Tool. The credential is an Epic Games Store credential, with a Publishing setting for studios that use their own self-service publishing tools. Agents report where the BuildPatch Tool is, and a project can set its own BuildPatch Tool folder.

Build chains

  • reverse.dep.<id>.<name> sets a parameter on a build configuration that this one depends on. dep.<id>.<name> reads a value from a dependency's build. %param% in a value is filled in from the current build's own parameters, so you enter a value once. The chain pages show which values were sent and where they came from.
  • A personal build of a dependency is never reused by a normal build. Side builds, composite builds and Matrix builds pass values correctly. The sender's build number is the real one.
  • Matrix blocks: the visual editor shows a Matrix block as one card with its axes. An include row can set where it runs. The console has a lane chip for each combination.

Projects tree

  • Your own order: administrators can put projects and build configurations in any order, with a Reorder dialog and a reorder mode in the tree. Everyone sees the same order.
  • Separators: administrators can add named separators to group items in the tree.

Perforce

  • View mappings as a table in the Perforce root form and in manual workspaces: each line is a row with its mode (include, exclude, overlay), and rows can be reordered. # comment lines are kept. It has a depot browser and suggestions, a quick-add bar and errors that say what is wrong. A preview shows what each line maps, and can count the files on request. Table and text stay in sync, and the saved text keeps the classic format. Stream workspaces show the stream's view read only; Limit View stays editable.

Agents and fixes

  • WebSocket by default: when the server's TCP agent port is off, agents connect over WebSocket by themselves. To turn this off, use -noWebSocketFallback.
  • On the file-serving address, a missing file shows a plain Page not found with no extra text, as before.

The Steam and Epic steps have not yet been tested against real store accounts. Try them on a test app or branch first.

1.7

Build 2.589-buildspawn.16.

Sign in and words

  • New sign-in page: the logo on the left, the form on the right, the branch lines behind. It follows the chosen theme, or the system's setting when the default theme is in use.
  • A folder is now a "Project" and a job is a "Build configuration" in Buildspawn's own pages and in the plugins we build ourselves. Only the words changed: links, saved settings and the API are the same.

New Item

  • A new New Item page: the name with a live check, an ID made from the project's ID and the name (you can edit it), the project it goes in (with a picker), Start from (Empty, Copy of an existing item, Template), the type as cards, and a summary. Create stays off until everything is valid and says why.
  • Types: Build configuration, Pipeline, Project, Build configuration template, and Multibranch Pipeline under More types. Multi-configuration project and Organization Folder are no longer offered; existing ones keep working.

Build configurations

  • The first five tabs are always Overview, Change Log, History, Statistics and Settings, whatever plugins a build configuration has. Pipelines get the History tab too.
  • Matrix mode for Parallel blocks: write the steps once, give the values (for example platform × config), exclude or add combinations, and every combination runs as its own side using %platform% and %config%. Choose where each combination runs, how many run at once, a Try first combination and what happens when one fails. The build page shows a grid of the results with Re-run for each combination, and the console has a lane for each. See Side builds.
  • New build step Perforce operations (group Source control): Sync, Clean, Reconcile, Edit, Add, Delete, Revert, Submit, Shelve, Unshelve, Delete shelf, Tag build changelist, Integrate, Copy, Merge, Resolve, Label, or any other p4 command. It uses the project's Perforce root (server, credential, workspace), so no password is typed into a step or shown in the log. Results such as a new changelist number go to the next steps. Dangerous commands are refused unless an administrator allows them under Settings › System › Perforce operations. The Administrator connection needs its own permission.

Agents

  • Built-in agent parameters: agent.name, agent.pool, agent.labels, agent.type, agent.owner, agent.executors, agent.hostname, agent.os.family, agent.os.version, agent.memory.total.mb, agent.version, agent.work.dir, agent.work.dir.free.mb, agent.home.dir and agent.temp.dir. Use them in agent requirements (for example agent.name matches WIN-BUILD-0[1-4], or agent.pool equals Unreal) and in steps as %agent.name%. Administrators can offer environment variables as env.NAME under Settings › System › Agent environment variables. Names that look like secrets are refused.

Forms and pages

  • Lists in settings (post-build actions, parameters, columns, filters and more) are rows in one card that fold, with a summary line, drag to reorder and remove. + Add opens a picker with search.
  • Advanced… is now More options, with how many options are set and which.
  • Few choices are buttons, long lists have search. Perforce workspace options and Roles permissions have plain names instead of codes.
  • Simple pages (Move, Rename and Delete of a build, build configuration or project, Replay, Rebuild, Restart from stage, label settings, Edit description) are one card: what will happen, the fields, and the buttons in the bottom bar. Deleting a project asks you to type its name.
  • Who am I, Project relationship and label pages have tabs instead of a side menu.
  • View settings: the list of build configurations has a search box, Select all / Clear and a count.
  • Error pages (page not found, no access, something went wrong) use the normal layout with a way back. Technical details are folded and shown to administrators only.

A few plugins we ship as published (Multibranch, JUnit, Pipeline steps help) still say job and folder in their texts.

1.6

Build 2.589-buildspawn.15.

Personal machines: run builds on your own computer

  • My machines (account menu): connect your own computer as a personal agent. Only you can build on it, and only your own builds run there. It is hidden from everyone else.
  • Run on my machine: start a build on one of your machines, either in its own copy of the workspace or in a folder you have already synced. A synced folder is never wiped or cleaned up. After the build, the shelved files are reverted, and only when the workspace has no other open files.
  • Share a build from your machine with a link. See Shared builds.
  • Builds are cancelled when your machine goes offline for longer than the time set under Settings › Security › Personal machines.
  • An administrator chooses which credentials personal machines may use; the rest are refused. The Use personal machines permission (Agent › UsePersonal) decides who can add one. See Personal builds and shelves.

Agent app and terminal view

  • Every agent download has a terminal view of its status: connection, current build, logs, workspaces and machine details. You can pause the agent (it finishes the current build first) or stop it from there.
  • On Windows an agent also comes with a notification-area app showing the same status, with Pause, Stop, Open logs and the connection history.
  • Agents report their state to the server every few seconds, so a paused or stopped agent shows why on its page and in the agents list.

Forms and pages

  • Every settings page uses the new form layout: an On this page index, the fields in cards, a summary card, real switches and choices instead of raw option text, help shown when you focus a field, checks when you leave a field, and advanced settings folded away. This covers system settings, security, build configurations and projects, agents, views, credentials, roles and permissions, Perforce, Vault, Unity, Unreal, telemetry and your user pages.
  • One Save / Apply / Cancel bar on every page. It stays at the bottom of the window, is as wide as the page content and never covers anything.
  • Build configuration settings tabs never hang on the loading placeholder. If a part takes long, it says so and offers Reload. Version Control and Post-build Actions open in under a second.
  • Projects and the root project show their pages as sub-tabs, like the build configuration settings, instead of a side menu.
  • The Build Queue and Executors side cards are gone. The Queue page and the Agents list show both.
  • Add Credentials no longer spins forever when you click it before hovering.

Permissions and logs

  • Project-based security keeps its 1.5 layout: one card for each user or group, with what it grants as a summary and every permission grouped inside the card. The Entra ID matrix now uses the same cards, with an Add from Entra ID row for the people picker, or a name box with Add user and Add group when Graph search is off.
  • No more warning in the log when an agent disconnects while its output is still being closed.

To serve Buildspawn under a path such as https://your-host/buildspawn/, add --prefix=/buildspawn to the extra arguments (Windows app: Settings › Advanced; or arguments= in buildspawn.cfg), then set the server URL in Settings › General.

1.4

Build 2.589-buildspawn.13. Install it over 1.2 or the 1.3 test builds.

Agents page

  • One list of agents. Online and offline agents are in one list, with All, Online and Offline, pool and platform filters, search, Warnings only, sorting and paging. The filters are kept in the address, so you can share a link to a filtered list.
  • Live columns for CPU, memory, disk, GPU, network, pressure and freshness, coloured by your thresholds.
  • Expanded rows show each busy executor's build: number, time, progress against the estimate, the current step and a stop button.
  • A row menu with Mark offline, Bring back online, Reconnect, Show connection log, Move to pool and Delete. Mark offline, Bring back online and Move to pool can be undone.
  • Unauthorized agents show only when some are waiting. Self-registration and rejected agents moved under Install agents › Agent registration.

Telemetry

  • On by default. Every agent is sampled every 30 seconds, and every 2 seconds while someone watches its Telemetry tab.
  • History for 15 minutes, 1 hour, 6 hours and 24 hours on each agent's Telemetry tab, with Live and Pause.
  • Settings live under Agents › Configure monitors. Each agent can opt out with Collect telemetry from this agent.

Pools and the Pool Scheduler

  • Each pool can have an icon and a colour. They show in the Agents sidebar, the Pools tab, the pool page and the move dialog. In the sidebar, pools open to show their agents as idle, busy or offline.
  • The Pool Scheduler moves agents between pools: by hand with Undo, on a weekly schedule, or with priority rules that borrow idle agents from lower-priority pools and give them back. It has Pause and an activity log. Renaming or deleting a pool or an agent updates the scheduler's rules.

Other changes

  • Documentation links on build configurations and projects, shown on a Documentation tab.
  • Agent downloads include Java 21: Windows x64, Linux x64 and ARM, macOS Apple silicon and Intel. An agent machine needs nothing installed first. The server file is about 450 MB then, because it carries Java for the five agent platforms.
  • The theme switch in the top bar is a plain Light / Dark toggle.
  • Windows: the app (Buildspawn.exe) is back next to the terminal program (bin\buildspawn.exe). The app shows the product version.
  • The recommended Java options now include --enable-native-access=ALL-UNNAMED. Existing settings files keep their own options. See Settings files.

1.2

Build 2.589-buildspawn.9.

The visual editor

  • A build configuration's steps are drawn as a graph you can edit: canvas, palette, wiring, undo, keyboard shortcuts and save. It is read only for people who can't edit.
  • One build configuration block holds the triggers, roots and settings. Parameters are a group wired into it, and each parameter lists the steps that use it.
  • A large properties dialog for each node, and a side panel that can stay open.
  • Per-step overrides: a step can run on another machine and override environment values.
  • Run view draws the latest or any chosen build over the graph, with live status.

Builds and steps

  • Parallel blocks: steps run side by side, on this machine or on others.
  • Resume and retry: resume a failed build from a step, or retry a step when it fails.
  • Wipe out workspace runs in the background with live progress.
  • The build console stays quick while a build streams long output.

Parameters and settings

  • One Parameters tab for configuration, env. and system. parameters. The time limit moved to the Build time card under Failure conditions.
  • %NAME% works in batch and shell steps too.
  • Every setting has its own place in the settings homes, for build configurations and for projects.
  • Projects can have a coloured icon. Favourite colours are shared with the team.

Top bar

  • Manage is now called Settings. My changes moved into the account menu.
  • A theme switch where the bell was. Warnings for administrators show as a count on Settings.
  • A waiting build can be moved to the front of the queue.

Terminal program

  • The terminal program, buildspawn, on every system. On a first run it opens a five-step launch flow: home folder, port and memory, service or portable, admin password, start. Presets save your answers, so you can set up the next machine the same way.
  • The live monitor has seven views: Overview, Builds, Queue, Agents, Logs, Service and Settings. The Queue view says why each build waits. With an API token the monitor can stop builds, cancel queue items and take agents offline.
  • The Service and Settings views install and control the service and edit the settings file. They ask for administrator rights only when needed.
  • Every view has a text command for scripts: status, builds, queue, agents, logs, service and set, with --json. See Terminal program commands.
  • Windows setup puts the terminal program on the PATH.

Security and fixes

  • A build can set parameters only with ##buildspawn[setParameter] service messages. Only env.NAME reaches the environment, and names that change how programs start are blocked.
  • People who may only view settings no longer see secret values.
  • A build no longer hangs at the end when its artifacts are kept in remote storage.
  • Moving or copying a step no longer turns inherited steps into copies.

1.0

The first release, shipped as three release candidates (builds 2.589-buildspawn.5 to .7).

Main features

  • Projects that pass their settings, steps and parameters down to the build configurations inside them. A build configuration can override or reset what it inherits.
  • Build configurations set up on separate pages: General, Version control, Build steps, Triggers, Failure conditions, Parameters, Build features and Agent requirements.
  • Templates, and several version control roots on one build configuration.
  • Runners for Command Line, Python, PowerShell, Maven, Gradle, Ant, .NET, NUnit, Node.js, Docker and more, plus Unity and Unreal Engine steps.
  • Parallel tests and composite builds.
  • Perforce connections, streams, shelves, review status and a workbench page.
  • Agents with install pages, requirements and telemetry.
  • Tools with several versions per tool and a %tool.id% parameter.
  • HashiCorp Vault secrets in parameters.
  • Versioned settings stored in Git or Perforce.
  • Users, groups and project roles, with pickers instead of typed names.
  • Most plugins come built in, so a new server works without downloads.
  • Windows setup with an optional Windows service, and a portable zip. Java is included.

Added during the release candidates

  • Faster Perforce pages: no page waits on the Perforce server. Lists of changes and shelves are stored and refreshed in the background.
  • The Run dialog opens at once and loads changes and shelves in the background.
  • A script editor for build steps, with colours, line numbers, search and % autocomplete of parameters. %name% references inside scripts, with safeguards for secrets.
  • Version control parameters such as %build.vcs.number% and %vcsroot.url%.
  • Re-run any finished build with the same sources and parameters, and Re-run with changes to pick other revisions or shelves.
  • Tabs that don't fit move into a More menu.
