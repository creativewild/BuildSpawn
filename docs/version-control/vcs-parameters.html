Version control parameters

Every build knows which code it checked out. Steps can read the commit, changelist, branch and folder as parameters.

You don't define these parameters: Buildspawn fills them in when the build starts. Use them to stamp a version into your game, to name a package after the changelist, or to find a second root on disk.

When to use it

Use these values to stamp a version into your game, name a package after the changelist, or find the folder of a second root.

Available parameters

About the build

ParameterWhat it holds
%build.vcs.number%The revision the build used: the Git commit or the Perforce changelist.
%build.branch%The branch or stream the build used.
%build.branch.isDefault%true when that is the default branch.
%build.vcs.branch.<root>%The branch of one root.
%build.checkoutDir%The folder on the agent where the code was checked out.
%build.changedFiles.file%The path of a file that lists the files changed since the last build, one per line.
%build.is.personal%true for a personal build, for example of a Perforce shelf.
%build.triggeredBy.username%The user ID of whoever started the build, or of the build chain. Empty for a schedule or a version control trigger. Also in the environment variable BUILDSPAWN_TRIGGERED_BY.

About each root

Replace <root> with the root's name. With only one root, you can leave it out: %vcsroot.url% works too.

ParameterWhat it holds
%vcsroot.<root>.url%The Git repository URL.
%vcsroot.<root>.branch%The branch the root is set to build.
%vcsroot.<root>.port%The Perforce server address.
%vcsroot.<root>.user%The user the root signs in as.
%vcsroot.<root>.changelist%The Perforce changelist that was synced.
%vcsroot.<root>.stream%The Perforce stream.
%vcsroot.<root>.shelvedChangelist%The shelf that was unshelved, in a personal build.

No password or token ever appears in these parameters.

Environment variables

The same values also reach every step as environment variables, for scripts that read the environment:

VariableWhat it holds
BUILD_VCS_NUMBERThe same as %build.vcs.number%.
VCS_ROOT_DIR_1, VCS_ROOT_DIR_2, …The folder of each root, when the build configuration has several.
P4_CHANGELISTThe Perforce changelist that was synced.
GIT_COMMIT, GIT_BRANCHThe Git commit and branch.
P4_PORT, P4_USER, P4_CLIENT, P4_ROOT, P4_TICKETThe Perforce connection, workspace and login ticket. See Perforce variables.
P4ROOT_<ID>_CHANGELIST and othersValues of one Perforce root, named after the root ID.
GIT_COMMIT_1, P4_CHANGELIST_2, …With several roots, each variable also exists with the root number at the end. The first root that sets a variable also sets the plain name.

Use them in steps

Type % in the script editor of a step to see the list. For example, put the changelist into the package name:

powershell -File Build\ci.ps1 -Stage package -Platform Win64 -Changelist %build.vcs.number%

Name each build after its code with a buildNumber message from a step. The build number format on Settings › General is applied before the checkout, so it cannot use these values:

Write-Host "##buildspawn[buildNumber '1.4.%build.counter%-CL%build.vcs.number%']"

Or only run a slow step for real code changes, not personal builds:

if "%build.is.personal%"=="true" (
  echo Personal build: skipping upload
) else (
  upload-build --changelist %build.vcs.number%
)

Branch names and other values from version control are put into script text only when they hold safe characters. A branch with odd characters is not expanded. In a script, prefer the environment variable.

What you see when it runs

On the build page, Parameters lists the values the build used. In the console, a step that prints %build.vcs.number% shows the changelist or commit.

Problems and fixes

You seeWhat to do
The value stays as %build.vcs.number%The build configuration has no version control, or the name is misspelled.
A branch name is not filled in inside a scriptIt has unsafe characters. Read the environment variable instead.
