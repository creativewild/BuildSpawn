Perforce operations

A build step that runs Perforce commands for you: sync, clean, submit, shelve, copy a stream and more, without a password in any script.

When to use it

Use it when a build must do more than the first sync. Typical jobs: clean the workspace before a build, submit a version file after the build, shelve generated files, copy one stream to another, or label what you built. The step uses the Perforce root of the build configuration, so the server, user and workspace are already set. The password stays in the connection. It is never typed into the step, put in a script or shown in the log.

The step does not start the p4 program. Buildspawn sends the commands to the server itself, so the agent does not need p4 installed.

How to set it up

  1. Open the build configuration and go to Settings › Build steps.
  2. Click Add build step, type Perforce in Filter step types and click Perforce operations.
  3. Under Connection, leave Use the project's Perforce root. The card below shows the root, server, user and workspace the step will use. Click Test connection to check them.
  4. Under Operation, click the card of the operation you want. The fields under Settings change to fit it.
  5. Fill in the fields. The Command box at the bottom shows the Perforce command the step will run.
  6. Under Options, choose what counts as a failure and what the step hands to the next steps.
  7. Click Save.

The build configuration needs a Perforce root as its version control. Without one the step stops with This job has no Perforce root.

An administrator connection has no workspace, so the operations that work on workspace files (sync, clean, reconcile, submit and the like) are not offered with it.

Every operation

The operations are in four groups. Each one lists the Perforce command it runs. Build parameters such as ${BUILD_NUMBER} can be used in the text fields.

Files

Sync: get files from the depot

Runs p4 sync. Use it to get a different revision, or more paths, after the first sync.

FieldWhat it does
FilesOne path per line, a depot path or a path in the workspace. Empty means the whole workspace.
RevisionA changelist, label or date, for example @48200 or @release-1.3. It is added to each path.
Force syncGets every file again, even those the workspace already has (-f).
Preview onlyLists what would change and changes nothing (-n).

Clean: put the workspace back to what the depot has

Runs p4 clean. It removes files the depot does not have (build output, for example), restores files you changed on disk and restores files that were removed. Before it changes anything it runs a preview and counts the files, so it can stop before it deletes too many.

FieldWhat it does
FilesWhich paths to clean. Empty means the whole workspace, and the form shows a warning: This touches the whole workspace.
Added filesDelete local files the depot does not have (-a).
Edited filesRestore files changed on disk to the depot version (-e).
Deleted filesRestore files removed from disk (-d).
Ignore .p4ignoreOff keeps the files your .p4ignore lists, such as Intermediate/, Saved/ and DerivedDataCache in an Unreal project. On cleans those too (-I).
Fail if more files would be deleted thanA safety limit. If the check finds more files to delete, nothing is deleted and the step fails. 0 means no limit.
Preview onlyLists what would change and changes nothing.

The three file kinds are all on when you open the form. If none is switched on, the step does all three.

Reconcile: open added, edited and deleted files

Runs p4 reconcile. Use it after a build that changed files you want to submit: it finds the changes on disk and opens the files in Perforce.

FieldWhat it does
FilesPaths to look at. Empty means the whole workspace.
ChangelistPut the opened files in this pending changelist. Empty uses the default changelist.
Added files, Edited files, Deleted filesOpen new files for add, changed files for edit, missing files for delete.
Preview onlyLists what would be opened and opens nothing.

Edit files, Add files, Delete files

Run p4 edit, p4 add and p4 delete. They open the files you name. The step stops with Enter the files, one per line if Files is empty.

FieldWhat it does
FilesOne path per line. Required.
ChangelistThe pending changelist to open them in. Empty uses the default changelist.
Preview onlyShows what would be opened.

Revert: undo opened files

Runs p4 revert. With no Files and Only files that are unchanged off, it reverts everything under the workspace (...).

FieldWhat it does
FilesPaths to revert.
ChangelistRevert only the files of this changelist.
Only files that are unchangedReverts only files with no edits. Files with edits stay open (-a).
Preview onlyShows what would be reverted.

Changelists

Submit: submit opened files

Runs p4 submit. You must give a Description or a Changelist, or the step stops with Enter a description or the number of a pending changelist. It hands the new changelist number to the next steps.

FieldWhat it does
DescriptionThe changelist description, for example Version bump for build ${BUILD_NUMBER}.
ChangelistA pending changelist number to submit. If you fill it in, it is used and the description is not.
Keep files checked outReopens the files after the submit, so later steps can go on editing them (-r).

Shelve: store opened files on the server

Runs p4 shelve. With no changelist number, it moves the files of the default changelist into a new changelist with your description, and shelves that. It hands the changelist number to the next steps.

FieldWhat it does
DescriptionThe description of the new changelist. Needed when Changelist is empty.
ChangelistAn existing pending changelist to shelve.
Replace the shelfRemoves the files already shelved in that changelist first (-r).

Unshelve: bring a shelf into the workspace

Runs p4 unshelve. Use it to put a shelved change into the workspace during a build.

FieldWhat it does
FilesWhich files of the shelf. Empty means every file of the shelf.
ChangelistThe shelved changelist, for example ${CHANGELIST}. Required.
TargetThe pending changelist to unshelve into. Empty means the default changelist.
Overwrite writable filesUnshelves over files that are open or writable (-f).
Preview onlyShows what would be unshelved.

To add a shelf to a build's changes as well, use Perforce root: unshelve.

Delete shelf: remove a shelf

Runs p4 shelve -d -c. Give the number of the shelved Changelist. Use it to tidy up shelves a build made.

Tag build changelist: add the build to a changelist description

Adds a line to the description of a changelist, so people looking at the changelist see which build used it.

FieldWhat it does
ChangelistThe changelist to tag. Empty means the changelist the build synced.
DescriptionThe line to add. Empty adds the build configuration name, the build number and its address.

Branching and labels

Integrate, Copy, Merge

Run p4 integrate, p4 copy and p4 merge. Integrate branches or merges between paths. Copy makes one path the same as another. Merge brings changes from a source into the target. The files are opened in your workspace. Use a Submit step after them to finish.

FieldWhat it does
SourceA depot path. Leave it empty if you name a branch mapping or stream below.
TargetThe target path.
Branch mapping or streamA name uses a branch mapping (-b). A path that starts with // uses a stream (-S); the Source is then the parent stream (-P).
ChangelistOpen the files in this pending changelist.
Preview onlyShows what would happen.

If you give no branch or stream, you must give both a Source and a Target. See Copy a stream.

Resolve: resolve files after a merge

Runs p4 resolve in automatic mode.

FieldWhat it does
FilesPaths to resolve. Empty means all files that need it.
How to resolveSafe (-as) resolves only files with no conflict. Merge (-am) merges what it can. Take theirs (-at) keeps the source. Keep yours (-ay) keeps the target. Default: Safe.
Preview onlyShows what would be resolved.

Label: create or update a label

Runs p4 labelsync, and p4 label first when you tick Create the label first.

FieldWhat it does
Label nameThe label. Required, for example skyforge-build-${BUILD_NUMBER}.
FilesWhich files to label. Empty labels everything in the label's view.
DescriptionThe label's description. Empty gives Created by the build.
Create the label firstOff updates a label that exists already. On makes a new one that maps //....

Anything else

Custom command

Runs any other Perforce command.

FieldWhat it does
CommandThe command alone, for example changes or fstat. It runs inside Buildspawn, not in a shell. A leading p4 is removed. A command with spaces, or one that starts with -, is refused.
ArgumentsOne argument per line, so spaces never need quoting. Example: -m on one line and 5 on the next.

Rules about dangerous commands

An administrator sets rules for every Perforce operations step in the Perforce operations section of the system settings.

SettingWhat it does
Allow destructive custom commandsOff (default): the custom command refuses obliterate, protect, triggers, typemap, admin, configure, unload, archive, deleting users, groups and depots, and -f on deleting a spec. Turn it on only on an instance you trust.
Allow Administrator connectionOff (default): steps use the Perforce root only. On: a step can choose an Administrator connection, when the person who sets it up has the Perforce permission Use administrator connection. Such a step runs without a workspace.

Commands that show or change a login (passwd, tickets, trust, set, logout, login -p) are always refused. A password or ticket in the output is replaced by ******** in the log.

A worked example

The Skyforge team builds an Unreal Engine game. Before each build they want a clean workspace but must keep Intermediate/ and Saved/ to save compile time. After a good build they submit a version file.

Step 1, Clean workspace:

OperationClean
Files//skyforge-win64-${NODE_NAME}/Game/...
Ignore .p4ignoreOff
Fail if more files would be deleted than2000

The last step, Submit version file, comes after an Edit files step that opened Config/Version.ini:

OperationSubmit
DescriptionVersion file for build ${BUILD_NUMBER}
Save the result as a step outputVERSION_CL

What you see when it runs

P4: buildbot@ssl:perforce.studio.example:1666 (Perforce root Skyforge Main) client buildspawn-win-build-01-Game-Windows-Build-0
$ p4 clean -a -e -d //skyforge-win64-win-build-01/Game/...
deleted: 214 files
    C:\ws\Game\Intermediate\Build\Win64\...
restored: 0 files
refreshed: 3 files

Each command is shown after a $. A clean prints how many files were deleted, restored and refreshed, then each file. A step output prints as P4: Step output VERSION_CL = 48512.
