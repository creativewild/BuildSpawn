Perforce variables

Every build with a Perforce checkout gets variables for the server, user, workspace, changelist and a login ticket, so your scripts can talk to Perforce.

When to use it

Use them in a script step that runs p4 commands, to stamp the changelist into a package, or to name a build after its code. You do not define them. Buildspawn fills them in when the build starts. For the full list of version control values, see Version control parameters.

The variables

VariableWhat it holdsExample
P4_PORTThe Perforce server connection.ssl:perforce.studio.example:1666
P4_USERThe Perforce user of the connection.buildbot
P4_CLIENTThe name of the workspace of this build.buildspawn-win-build-01-Game-Windows-Build-0
P4_ROOTThe folder of the workspace on the agent.C:\ws\skyforge
P4_CHANGELISTThe last changelist in the synced workspace. If none is found, the latest changelist on the server.48512
P4_TICKETA valid login ticket for the connection. Shown only if the connection could log in, and only when Hide TICKET is off (see below).
P4_REVIEW, P4_REVIEW_TYPEThe Swarm review number and its type, shelved or committed, for a build of a review.1024, shelved
P4_STREAM_AT_CHANGEThe Stream at change value of a stream workspace.
P4_INCREMENTALWith the Polling per change filter: set it to false to build all changelists, not only the oldest.

Variables of a Perforce root

With a Perforce root, a build also gets variables named after the root. Replace <ID> by the root ID in capitals, with letters other than A to Z and 0 to 9 turned into _. A root skyforge-main becomes SKYFORGE_MAIN.

VariableWhat it holds
P4ROOT_<ID>_PORT, P4ROOT_<ID>_USERThe server and user of the root.
P4ROOT_<ID>_CLIENTThe workspace of this build.
P4ROOT_<ID>_CHANGELISTThe changelist that was synced.
P4ROOT_<ID>_STREAMThe stream of this build.

The first root of the build configuration also sets P4PORT, P4USER and P4CLIENT (no underscore), the names the p4 program reads. A plain p4 changes in a script then works without options. These never hold a password or ticket. With several roots, each variable also exists with the root number at the end, such as P4_CHANGELIST_2.

Hide the ticket

In the system settings, the Perforce section P4: Secure P4_TICKET has the switch Hide TICKET. Off (the default) puts P4_TICKET into the environment of every build step. On removes it. Turn it on if people who can edit build steps should not be able to read the ticket. The value is a secret: scripts must not print it. See Use P4 commands in a script with the P4 ticket.

The changelist in the build name

A build is numbered before the checkout, so the number format on Settings › General cannot hold the changelist. Name the build from a step instead. Print a buildNumber message:

echo ##buildspawn[buildNumber '1.4.%build.counter%-CL%build.vcs.number%']

In a PowerShell step write:

Write-Host "##buildspawn[buildNumber '1.4.%build.counter%-CL$env:P4_CHANGELIST']"

The last name printed wins. See Service messages.

A worked example

A Skyforge packaging script writes the changelist into the version file and names the build:

Set-Content Config\Version.txt "CL $env:P4_CHANGELIST"
Write-Host "##buildspawn[buildNumber '2.3.%build.counter%-CL$env:P4_CHANGELIST']"

What you see when it runs

On the build page, the build is called 2.3.57-CL48512. The Parameters list shows P4_CHANGELIST and the other values, but not the ticket.

Problems and fixes

You seeWhat to do
P4_TICKET is emptyCheck that Hide TICKET is off and that the credential can log in.
P4_CHANGELIST is emptyThe step ran before a checkout, or the build configuration has no Perforce version control.
A plain p4 asks for a passwordThe standard variables carry no password. Log in with the ticket: p4 -P %P4_TICKET% ....
