Backups and upgrades

Keep your data safe and move to new versions of Buildspawn without losing anything.

Everything Buildspawn knows is in one folder, the home (also called the data folder): projects, build configurations, build history, users, credentials, settings and plugins you added. The program files are separate and can be replaced at any time. Back up the home folder and you can always get back.

The same folder also holds secrets\ (with initialAdminPassword on a new server), trust\ (your trusted certificates) and users\. The full list is in Inside the data folder.

The settings file can move the home somewhere else. Check the data or BUILDSPAWN_HOME key, or see Settings › System › Home directory. The keys are listed in Settings files.

Back up

  1. Stop Buildspawn, or click Prepare for Shutdown on the Settings page so no build is writing files. A copy taken while builds run can be incomplete.
  2. Copy the whole home folder to a safe place, for example another disk or a network share.
  3. Copy the settings file too (buildspawn.cfg or buildspawn.conf).
  4. Start Buildspawn again.

Example on Linux with a package install:

sudo systemctl stop buildspawn
sudo tar -czf /backup/buildspawn-$(date +%F).tar.gz -C /var/lib buildspawn /etc/default/buildspawn
sudo systemctl start buildspawn

Example on Windows, in a command prompt opened as administrator:

cd "C:\Program Files\Buildspawn"
buildspawn-service stop
robocopy C:\ProgramData\Buildspawn D:\Backup\Buildspawn /MIR /XD logs
buildspawn-service start

What you can leave out

The home folder can be large because of build history and artifacts. If space is short, these are safe to skip:

  • workspace/: working copies of the sources. Builds check them out again.
  • war/: unpacked again when Buildspawn starts.
  • The logs folder.

Always keep the secrets/ folder and the secret.key files in the home folder together with the rest. Without them, Buildspawn cannot read the saved passwords and credentials.

Prepare for shutdown, and reload

Two buttons on the Settings page help around a backup or an upgrade.

  • Prepare for Shutdown stops new builds from starting so the system can be shut down safely. Running builds finish. You can type a Reason: it is shown to everybody in a banner at the top of every page until you click Cancel Shutdown. Use it before a backup, a restart or an upgrade. Click Update shutdown preparation to change the reason.
  • Reload Configuration from Disk throws away everything the server holds in memory and reads it all again from the data folder. Use it after you changed files in the data folder by hand, or put back part of a backup, when you cannot restart the server. A restart is safer after a full restore.

Restore

  1. Install the same version of Buildspawn, or a newer one.
  2. Stop Buildspawn.
  3. Replace the home folder with your backup, and put back the settings file.
  4. On Linux with a package or service, give the files back to the service user: sudo chown -R buildspawn:buildspawn /var/lib/buildspawn.
  5. Start Buildspawn and sign in with your usual account.

Try a restore once on a spare machine. A backup you have never restored is only a hope.

Upgrade

An upgrade replaces the program and keeps your home folder and settings. Back up first, then follow the steps for your download.

Windows setup

  1. Download the new buildspawn-<version>-setup.exe and run it.
  2. The setup stops the service, replaces the program files, keeps your settings and data, and starts the service again.

For a silent upgrade, run setup.exe /S. setup.exe /? lists every switch. See The Windows app.

Windows portable zip

  1. Stop Buildspawn in the app (Run here › Stop, or stop the service).
  2. Unpack the new zip into a new folder.
  3. Copy buildspawn.cfg and data\ from the old folder into the new one.
  4. Start the new Buildspawn.exe. If you used the Windows service, install it again from the new folder.

Linux packages

Install the new package over the old one:

# Debian, Ubuntu
sudo apt install ./buildspawn_<version>_amd64.deb

# RHEL, Rocky, Fedora
sudo dnf install ./buildspawn-<version>.x86_64.rpm

The upgrade stops the service, replaces the program, keeps the settings file and /var/lib/buildspawn, and starts the service again.

Linux and macOS tar.gz

  1. Stop Buildspawn: bin/buildspawn stop.
  2. Unpack the new version into a new folder. On macOS, clear its quarantine flag as described in Install the server.
  3. Copy buildspawn.conf and data/ into the new folder (and logs/ if you want to keep them).
  4. If you run Buildspawn as a service, run the new version's install-service.sh (with sudo on Linux, without on macOS). It points the service at the new folder.
  5. Start it: bin/buildspawn start.
$ bin/buildspawn stop
$ tar -xzf buildspawn-<version>-linux-x64.tar.gz -C /opt
$ cp /opt/buildspawn-old/buildspawn.conf /opt/buildspawn-<version>/
$ cp -a /opt/buildspawn-old/data /opt/buildspawn-<version>/
$ cd /opt/buildspawn-<version> && sudo ./install-service.sh

To make tar.gz upgrades simpler, set BUILDSPAWN_HOME to a folder outside the program folder, such as /srv/buildspawn. Then an upgrade only needs the settings file copied.

The war file

The war is the web application on its own, for people who run it with their own Java. It is a single file, buildspawn-<version>.war, and Java 21 or newer must be installed. The data folder is the one you name with the home setting you start Java with, so it is outside the war and an upgrade does not touch it.

  1. Back up the data folder as described above.
  2. Stop the running Buildspawn (end the java process or stop the service you made for it).
  3. Start the new war with the same data folder and the same arguments, for example java -jar buildspawn-<version>.war --httpPort=8080.

The old war can be deleted once the new one runs. Keep it until then, so you can go back.

After an upgrade

  • Check Settings for new notices (the red number in the top bar).
  • If you changed the Java options by hand, compare them with the new recommended set. On Windows, use Reset to recommended in the app's Settings tab. See Settings files.
  • Read what changed in the release notes.

Tips

  • Run Buildspawn either as the service or by hand on one home folder, never both at once.
  • Back up on a schedule, for example every night, and keep several copies.
  • Don't skip versions when the release notes say a step is needed.
