Security realms

A security realm decides where the list of users comes from and how people prove who they are when they sign in.

When to use it

Pick the realm once, when you set up the server, and change it only when your company changes how it manages accounts. The realm answers "who are you?". A second choice, the authorization strategy, answers "what may you do?". The two are set on the same page and work together.

The five realms

RealmWhere users come fromUse it when
Buildspawn’s own user databaseA list kept by the server itself. You create the users, and they sign in with a user name and password.A small team, or a first test. No other system is needed. See Users and groups.
Delegate to servlet containerThe web server that runs Buildspawn (a servlet container such as Tomcat) signs people in.You run Buildspawn as a web application inside such a container that already handles sign-in. The standard server and the Windows and Linux packages do not use a container, so you will not need it.
Entra IDYour company's Microsoft Entra ID directory. People sign in with their work account.Your company uses Microsoft 365 or Azure. See Entra ID sign-in.
miniOrange SAML 2.0Any identity provider that speaks SAML 2.0, for example Okta, Keycloak or Active Directory Federation Services.Your company uses single sign-on with SAML. See SAML sign-in.
NoneNobody signs in. Every visitor is the anonymous user.Only a throw-away test on one computer. Anyone who can reach the address uses the server.

How to set it up

  1. Open Settings › Security. You need the Administer permission.
  2. Find the section Security Realm. The page also has a Summary card on the right. It says in one line who can sign in and what decides what they may do.
  3. Open the drop-down and pick a realm. The fields for that realm appear below it.
  4. Fill in the fields (see below), then click Save.

Do not lock yourself out. Before you save a new realm, make sure the authorization grants Administer to a user that exists in the new realm. A user called dana in your own database is not the same person as dana@studio.example in Entra ID. If nobody can administer after the change, you cannot open Settings.

Switch safely

  1. Keep the current browser tab open and signed in. Open a second private window for the test.
  2. Set up the new realm and its authorization so that your future sign-in name has Administer. For Entra ID, add yourself in the Entra ID matrix before you save.
  3. Click Apply, or Save, and sign in from the private window.
  4. Close the first tab only when the private window works.

If you are locked out

You can turn security off on the server, then set it up again:

  1. Stop the server.
  2. Open config.xml in the Buildspawn home folder with a text editor.
  3. Change <useSecurity>true</useSecurity> to false.
  4. Start the server. Anyone can now open it. Go to Settings › Security and fix the realm and authorization straight away.

Copy the home folder first. See Backups and upgrades.

Delegate to servlet container

This realm has no fields. Buildspawn asks the container which user is signed in and which roles that user has. The names you type in the permission grid must match the role names the container uses.

A worked example

A studio starts with Buildspawn’s own user database. The administrator dana.k creates accounts for the team. Later the studio moves to Entra ID. Dana first adds her own work account (dana.k@studio.example) to the Entra ID matrix with Administer, tests it in a private window, and only then saves. The team signs in with their work accounts from that day on.

What you see when it runs

  • The Summary card says, for example, Users from Entra ID sign in; Entra ID Matrix-based security decides what they may do.
  • People who are not signed in are sent to the realm’s sign-in page. With Entra ID or SAML they go to your company’s sign-in page and come back.
  • Sessions that were open before keep working until they end or are terminated. See Users and groups.

Problems and fixes

ProblemWhat to do
After saving you see Access denied, or cannot open Settings.Your new sign-in name does not have Administer. Use the recovery steps above.
Old users from the own database still appear in lists.User records are kept when you change realm. They are harmless, and come back if you switch back.
Scripts that used a user name and an API token stop working after the switch.The token belongs to the user record. Sign in once with the new realm, create a new token and update the script. See API tokens.
With None, anyone can change things.Nobody can sign in, so whatever the authorization gives to Anonymous applies to every visitor. Choose another realm for any server other than a private test.
